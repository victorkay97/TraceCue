# TraceCue 0.2 — Recording, issue clips and engineering handoff

Updated: November 16, 2026. This document describes the implemented development branch and explicitly separates automated verification from Chrome acceptance testing.

## 1. Companion UX

- Clicking the TraceCue toolbar icon on an authorized HTTP(S) tab opens the native Chrome sidebar and injects the floating TraceCue mascot in the bottom-right corner.
- The mascot expands to show Start, Stop, issue title and lookback buttons (15, 30, 60, 120 seconds). A custom popup window is also accessible from the sidebar.
- Recording is explicitly started by the tester. Toolbar activation alone must never start surveillance.
- Capture uses Chrome tabCapture plus an offscreen document. Only one tab can be recorded at a time.
- Chrome may require the trusted sidebar Start button to grant a tabCapture stream ID. If a floating-button request cannot start video, TraceCue displays an error and the user must start from the sidebar.
- Only the selected origin is authorized. Cross-origin navigation stops recording, while same-origin page navigations can continue.
- The native tab video and diagnostic capture have previously been tested in Chrome; sidebar + mascot behavior is newly implemented and needs live re-validation.

## 2. Full session and per-issue clips

- The recording continues until the user clicks Stop, changes origin, closes the tab or capture otherwise ends. Marking an issue does **not** call Stop.
- Each issue marker stores a short title, unique ID, timestamp and requested lookback duration.
- The local viewer preserves the complete WebM blob independently from the clips.
- The clip start is max(video start, issue time minus lookback); clip end is the issue timestamp, clamped to available video duration. Only time *before* the mark is included.
- The first three marked clips are automatically generated while the review page remains open. More are generated by selecting **Generate remaining clips** or an individual Generate button.
- Clips are separately stored as WebM blobs in the same extension-origin IndexedDB object store, under keys prefixed with `clip:`. They can be previewed or downloaded individually. Deleting a session also removes its clips.
- Current clip creation uses an in-browser video playback stream and MediaRecorder re-encoding, which requires approximately real-time playback of each selected interval. The original WebM is not cut or overwritten.
- Close/reload during rendering may interrupt a clip. The original full video remains available; the viewer will offer generation again.
- This is not a low-latency, independent rolling-buffer capture engine. Standalone clip decoding and seekability need testing on a real Windows Chrome recording.

## 3. Studio evidence synchronization

- Import redacted session JSON as before, then attach the full video with **Attach full WebM**.
- The video remains in the browser as a blob object URL. Nothing is uploaded to Firebase or GitHub.
- Clicking an event in the timeline or an AI EV reference seeks to the appropriate timestamp relative to `videoStartedAt`, with `startedAt` as a fallback for earlier reports.
- During playback, the nearest event (within 2.5 seconds) is highlighted.
- Issue markers have dedicated jump buttons. Downloaded issue clips are separate WebM files; the current Studio inspector accepts the full recording, not a multi-file clip library.
- The browser must decode the WebM and provide usable seek behavior. Timing can be approximate when an older recording has no precise video start timestamp.

## 4. Reproducibility review and GitHub handoff

- TraceCue has a deterministic evidence catalogue separate from AI interpretations.
- The GitHub issue handoff checks for test prerequisites, expected behavior, actual behavior, manually reviewed reproduction steps, a repeat test, privacy review, authorization and relevant captured evidence.
- These are **tester attestations**, not proof of a defect. An unverified AI suggestion is never independently labeled a confirmed bug.
- The handoff remains an editable preview and does not publish the issue automatically. The tester explicitly copies the issue draft and opens the GitHub issue form, then submits manually.
- A synthetic GitHub API round-trip was verified in the owner's TraceCue repository: [integration issue #2](https://github.com/victorkay97/TraceCue/issues/2) was created with fictional evidence and closed successfully. This verifies account-side GitHub issue creation, **not** Studio OAuth/API publishing.

## 5. Public demonstration

The Studio is configured as a static Vite site with the `studio/` project root on Vercel.

- Current deployed URL: https://tracecue-studio-preview.vercel.app/
- Vercel returned deployment state **READY** for development-branch commit `4ce2aa2e764bacfcd051fc19d4367fd382ca4859`.
- The project was configured without Vercel Authentication for the public fictional preview.
- **Try fictional demo** loads `studio/public/demo-session.json` and clearly identifies it as synthetic.
- No user recording, Chrome extension storage, App Check debug token or private Firebase credential was included in the deployed build.
- Cloud AI on the public domain requires the Firebase project's public web configuration to be added as Vercel environment variables, **and** the actual `vercel.app` domain to be added to the production Fraud Defense key's verified domains. Don't weaken domain verification or publish debug tokens. The public demo therefore must not be advertised as a verified live cloud-AI deployment until separately tested.
- Localhost on-device and cloud Firebase inference have both already been confirmed by the tester on Chrome.

## 6. Chrome acceptance test

1. Pull `feat/tracecue-foundation`, open `chrome://extensions`, and reload TraceCue 0.2.0.
2. Open the authorized local QA fixture at `http://127.0.0.1:5173/qa-fixture.html`.
3. Click the TraceCue toolbar icon. Confirm the sidebar appears and the floating mint mascot appears in the lower-right corner.
4. Open the mascot, start a tab recording. If Chrome denies capture from the in-page button, use **Start recording** inside the sidebar. Confirm the red recording indicator and timer.
5. Trigger the fixture's intentionally failed save. After 30 seconds of additional test activity, mark an issue with **previous 30 seconds**.
6. Continue interacting for another 10–20 seconds. Confirm the mark did not stop the recording; then choose Stop.
7. In the local viewer, check that the entire WebM covers the full interval, the marked clip window is correct, and a playable **separate** WebM is saved after rendering completes.
8. Export the redacted JSON and full WebM; import both in Studio. Click an event/EV reference and confirm seeking and playback highlighting.
9. Import or generate a reviewed AI investigation, fill the reproducibility attestations, and verify that GitHub Copy/Open actions stay disabled until all checks are complete.
10. Try the deployed fictional demo. Test separately if/when Firebase production environment variables and Fraud Defense domain authorization have been configured.

## Known gaps / required follow-up

- Chrome sidebar, floating injection and MediaRecorder clipping were not exercised by an automated Chrome browser in this commit; test in the actual Chrome extension environment before a public functionality claim.
- Very long recordings are stored as an in-memory chunk array until Stop; multi-hour or crash-recoverable recording needs a segmented durable-write architecture.
- The clip exporter encodes in real time and is not instant; media seeking may need further WebM duration/index fixes on some Chrome versions.
- The public Vercel deployment runs a fictional demo without production Firebase configuration.
- GitHub issue posting is manual, so the product has no server-side credential handling or automatic external issue creation.

# TraceCue 0.3 — Recording, editing, issue evidence and engineering handoff

Updated: November 16, 2026. This document describes the implemented development branch and explicitly separates automated verification from Chrome acceptance testing.

## 1. Companion UX

- Clicking the TraceCue toolbar icon on an authorized HTTP(S) tab opens the native Chrome sidebar and injects the floating TraceCue mascot in the bottom-right corner.
- Before capture, the in-page mascot can expand to show Start, Stop, issue title and lookback buttons (15, 30, 60, 120 seconds).
- **Recording privacy:** Chrome tabCapture captures visible webpage layers, including DOM-injected widgets. TraceCue now removes the in-page mascot BEFORE MediaRecorder starts, and does not re-inject it on same-origin navigations while recording. It only restores the mascot once the full video is finalized. If the removal cannot be confirmed, recording fails closed instead of risking an overlay in the video.
- While recording, the tester can still see and use the mascot in Chrome's native side panel or its separate floating popup window, both outside the tab-capture surface.
- The floating popup is positioned near the browser's lower-right corner when opened. Chrome's standard extension windows API does not guarantee always-on-top; it may move behind the main window. The native sidebar is the reliably visible option.
- The sidebar lists every marked issue with its individual title, timestamp and lookback duration during recording.
- Recording is explicitly started by the tester. Toolbar activation alone must never start surveillance.
- Capture uses Chrome tabCapture plus an offscreen document. Only one tab can be recorded at a time.
- Chrome may require the trusted sidebar Start button to grant a tabCapture stream ID. If a floating-button request cannot start video, TraceCue displays an error and the user must start from the sidebar.
- Only the selected origin is authorized. Cross-origin navigation stops recording, while same-origin page navigations can continue.
- The native tab video and diagnostic capture have previously been tested in Chrome; sidebar + mascot behavior is newly implemented and needs live re-validation.

## 2. Full session and per-issue clips

- The recording continues until the user clicks Stop, changes origin, closes the tab or capture otherwise ends. Marking an issue does **not** call Stop.
- Each issue marker stores an **independent** short title, unique ID, timestamp and requested lookback duration. Example: "Name mismatch" for the previous 30 seconds and "Save button not responding" for a later 30-second interval.
- Titles are set when Mark is clicked, and can be edited after recording in the local viewer. Each clip also accepts its own tester notes (expected/actual behavior), not only session-wide notes.
- Individually downloaded WebM files include both the immutable marker ID and a safe filename slug derived from the title. Renaming an issue does not break its video association.
- The viewer can export separate per-issue Markdown and JSON draft reports restricted to that issue's clip interval; no full session video or unrelated events are included in an individual issue draft.
- The local viewer preserves the complete WebM blob independently from the clips.
- The clip start is max(video start, issue time minus lookback); clip end is the issue timestamp, clamped to available video duration. Only time *before* the mark is included.
- The first three marked clips are automatically generated while the review page remains open. More are generated by selecting **Generate remaining clips** or an individual Generate button.
- Clips are separately stored as WebM blobs in the same extension-origin IndexedDB object store, under keys prefixed with `clip:`. They can be previewed or downloaded individually. Deleting a session also removes its clips.
- Current clip creation uses an in-browser video playback stream and MediaRecorder re-encoding, which requires approximately real-time playback of each selected interval. The original WebM is not cut or overwritten.
- Close/reload during rendering may interrupt a clip. The original full video remains available; the viewer will offer generation again.
- This is not a low-latency, independent rolling-buffer capture engine. Standalone clip decoding and seekability need testing on a real Windows Chrome recording.

## 3. Studio evidence synchronization

- Import redacted session JSON as before, then attach the full video with **Attach full WebM**.
- The video remains in the browser as a blob object URL. Nothing is uploaded to Firebase or GitHub.
- Clicking an event in the timeline or an AI EV reference seeks to the appropriate timestamp relative to `videoStartedAt`, with `startedAt` as a fallback for earlier reports.
- During playback, the nearest event (within 2.5 seconds) is highlighted.
- Issue markers have dedicated jump buttons. Downloaded issue clips are separate WebM files; the current Studio inspector accepts the full recording, not a multi-file clip library.
- The browser must decode the WebM and provide usable seek behavior. Timing can be approximate when an older recording has no precise video start timestamp.

## 4. Reproducibility review and GitHub handoff

- TraceCue has a deterministic evidence catalogue separate from AI interpretations.
- The GitHub issue handoff checks for test prerequisites, expected behavior, actual behavior, manually reviewed reproduction steps, a repeat test, privacy review, authorization and relevant captured evidence.
- These are **tester attestations**, not proof of a defect. An unverified AI suggestion is never independently labeled a confirmed bug.
- The handoff remains an editable preview and does not publish the issue automatically. The tester explicitly copies the issue draft and opens the GitHub issue form, then submits manually.
- A synthetic GitHub API round-trip was verified in the owner's TraceCue repository: [integration issue #2](https://github.com/victorkay97/TraceCue/issues/2) was created with fictional evidence and closed successfully. This verifies account-side GitHub issue creation, **not** Studio OAuth/API publishing.

## 6. Chrome acceptance test

1. Pull `feat/tracecue-foundation`, open `chrome://extensions`, and reload TraceCue 0.2.0.
2. Open the authorized local QA fixture at `http://127.0.0.1:5173/qa-fixture.html`.
3. Click the TraceCue toolbar icon. Confirm the sidebar appears and the in-page mint mascot appears in the lower-right corner **before** recording. Open the optional separate controls window and inspect its position.
4. Open the mascot, start a tab recording. If Chrome denies capture from the in-page button, use **Start recording** inside the sidebar. Confirm the **in-page mascot disappears before recording** but the sidebar and optional companion window remain visible and responsive. Record a video and check the beginning/middle/end to ensure no TraceCue DOM widget is captured.
5. Trigger the fixture's intentionally failed save. Mark a **30-second** interval titled "Profile save failed"; continue testing, then mark a second 15-second interval titled "Name mismatch". Confirm the sidebar lists both independently while video recording continues.
6. Continue interacting for another 10–20 seconds. Confirm the mark did not stop the recording; then choose Stop.
7. In the local viewer, confirm the entire WebM covers the full interval **without the mascot**; check that two separate playable WebMs are saved under separate IDs and filenames. Rename one issue, add its own notes, then download its Markdown and JSON draft. Confirm those drafts exclude evidence from the other marker's time window.
8. Export the redacted JSON and full WebM; import both in Studio. Click an event/EV reference and confirm seeking and playback highlighting.
9. Import or generate a reviewed AI investigation, fill the reproducibility attestations, and verify that GitHub Copy/Open actions stay disabled until all checks are complete.
10. Try the deployed fictional demo. Test separately if/when Firebase production environment variables and Fraud Defense domain authorization have been configured.

## Known gaps / required follow-up

- Chrome sidebar, floating injection and MediaRecorder clipping were not exercised by an automated Chrome browser in this commit; test in the actual Chrome extension environment before a public functionality claim.
- Very long recordings are stored as an in-memory chunk array until Stop; multi-hour or crash-recoverable recording needs a segmented durable-write architecture.
- The clip exporter encodes in real time and is not instant; media seeking may need further WebM duration/index fixes on some Chrome versions.
- The public Vercel deployment runs a fictional demo without production Firebase configuration.
- GitHub issue posting is manual, so the product has no server-side credential handling or automatic external issue creation.

## Privacy acceptance rule (non-negotiable)

In-tab DOM widgets are **not** guaranteed to be invisible to Chrome tab capture. For a clean video, only out-of-tab controls may remain visible while recording. Don't use CSS overlays, a compositor blur, or video masking as proof of exclusion. The browser acceptance test must inspect the saved WebM itself. Future work may explore a native always-on-top companion, but the current Chrome popup is not guaranteed to stay on top.


## 7. Editable clip windows, post-marker buffer and complete issue evidence

This section supersedes earlier descriptions that only covered pre-marker video.

- Recording defaults: each marker has a selectable 15/30/60/120-second lookback plus a separate 0/5/10-second post-marker buffer; **+5 seconds** is selected by default on new markers. Older marker exports without this field retain +0 seconds for compatibility.
- At review, **Start / End** numerical fields are editable in tenths of seconds. Tester can **Preview interval**, then **Apply trim**. A **Reset to marker** option restores original lookback/post-buffer behavior.
- An applied trim updates the marker's timing, invalidates its previously encoded clip, and requires generating a new independent WebM. The full original WebM is never overwritten. This avoids showing a stale video with new labels or evidence.
- A post-marker buffer is limited to what was actually recorded. If Stop occurs before the buffer finishes, the interval ends at the available last frame. No video frames are invented.
- Each issue includes its own **Technical evidence** inspector, with Console / Network / Actions / Environment filters and a text search. The inspector follows its video window, so extending, shortening, or moving the clip changes which recorded events are included.
- Captured signals now cover user actions, warning/error/exception logs, console.info/log/debug, failed network requests and successful XHR/fetch response **metadata** (HTTP status, method, sanitized path and approximate duration), and limited environment metadata. The capture intentionally excludes raw request/response bodies, cookies, and authentication headers. Redaction is best effort.
- New grouped console events retain sampled per-occurrence timestamps, so an event group crossing a clip boundary can be attributed more precisely. Older reports without those timestamps may display an approximate event time.
- Individual clip exports now include all captured evidence events in that time window (subject to the whole session's maximum 4,000 recorded events); the viewer paginates long event lists for performance instead of silently dropping data.
- Each issue report separately records tester-rated severity, retest status, expected behavior, actual behavior, reproduction notes and additional observations. These are **human-entered facts**, not verified AI assertions.
- A tester can **Copy report**, download Markdown, download time-scoped JSON, and download a video clip independently.
- The issue video and its event window share the full recording's video clock. Playing a generated clip highlights the nearest visible event; clicking an event seeks to that moment in the original recording.

### Video editing acceptance criteria

1. Record the intentionally failing save, wait, and mark it with 30 seconds before + 5 seconds after.
2. Later, trigger fictional name mismatch and mark it 15 seconds before + 10 seconds after.
3. Stop and ensure there is one full recording and two independently named clips.
4. Open the first issue. Set Start to 3 seconds later and End to 2 seconds later than the current start/end, then Apply trim. Confirm evidence outside the new window disappears from that issue and the old encoded clip is invalidated.
5. Generate the revised clip; verify it plays, its duration approximates the chosen interval, and only its own filtered logs and actions appear.
6. Confirm the second issue's video, evidence, notes and identity are unchanged.
7. In the issue report, check the HTTP response status, console events, times, severity and reproduction fields. Confirm no raw bodies, cookies, authentication headers or unrelated issue logs are included.
8. Confirm the in-page mascot never appears in any captured frame.

**Not yet verified in live Chrome:** exact WebM encoding/seeking, playback sync and clip-boundary updates. Automated Node tests cover timestamp math, clip evidence scoping and redaction, and Studio build/syntax checks; live video needs the tester's desktop browser.


### One-pass QA specialist acceptance scenario (recommended)

Use the local fixture's controls in one recording, without any credentials or real-user data:

- At ~00:20 trigger **Name mismatch**, mark *Name mismatch* with 15s before / +5s after.
- At ~01:05 trigger **Failed save**, mark *Save failed* with 30s before / +10s after.
- At ~01:40 trigger **Trace console info & successful fetch**, mark *Successful request trace* with 15s before / 0s after.
- Stop after ~02:00. This should preserve one continuous full video and three separately named issue packages.
- Inspect the name-mismatch card's window: only matching interval signals should appear. Expand the save-failure interval, observe its network error/console exception, and search the successful-trace interval for \`console-info\`, \`console-debug\`, and \`network-response\` status 200.
- Manually trim the failed-save interval, confirm its event list changes, and regenerate its WebM while the other clips remain unchanged.
- Download or copy each individual issue draft and check that all captured events for that interval are present, not limited to the first 200.
- Check full WebM carefully for accidental mascot frames, clip audio/video sync, timekeeping, recording persistence and anything missing from logs.

You may adjust the approximate fixture test times. **The timeline is an example, not an automatic scheduled recording**. If errors are not captured, record the discrepancy and do not fabricate expected output.
